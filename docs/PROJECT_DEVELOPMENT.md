# 5DMind 项目开发文档

## 1. 项目概述

### 1.1 产品定义

5DMind 是一种面向复杂思考、研究和决策的对话工作台。它借鉴 5D 象棋的体验隐喻：用户不只在一条聊天记录上前进，也可以在历史节点上“回到过去”，开辟另一条时间线，再把不同时间线的结论进行比较和汇总。

产品要解决的问题是：

- 普通聊天把不同假设混在同一条上下文里，回溯成本高。
- 用户为了比较多个方案，不得不复制对话、手工记录差异。
- 长对话里重要决策、证据和上下文难以定位。
- AI 生成的答案具有探索性，但探索过程通常不可见、不可组织。

### 1.2 与 5D 象棋的对应关系

| 5D 象棋概念 | 5DMind 对应物 | 产品含义 |
| --- | --- | --- |
| 棋盘 | 时间线画布 | 展示多个并行上下文 |
| 棋子 | 消息/事件节点 | 每一步都改变对话状态 |
| 时间线 | 分支链 | 表示一组连续假设 |
| 穿越 | 从历史节点创建分支 | 在不破坏原对话的情况下重新探索 |
| 将军/威胁 | 决策约束或冲突 | 提醒用户某结论影响了其他路径 |
| 多盘联动 | 跨分支引用/合并 | 将一个分支的结果带入另一个分支 |

这里是交互类比，不是规则照搬。5DMind 不需要模拟棋类胜负，也不应要求用户学习复杂棋规。

### 1.3 可行性评估

#### 结论

方向可行，但不能把每条消息直接抽象成棋子。对话的主要任务是阅读、输入和理解连续上下文，棋盘的主要任务是导航、组织和比较结构。建议采用“普通对话为主 + 可展开结构地图为辅”的方案：聊天区域承载内容，地图承载时间线、分支、跨盘关系和风险标记。

#### 主要价值

- **探索价值**：同一问题可以并列尝试多个假设、提示词或方案。
- **认知价值**：用户能看到答案如何由上下文演化而来。
- **决策价值**：对比不同路径的结论、证据、代价和未解决问题。
- **复用价值**：分支可以保存为模板、研究结论或任务上下文。

#### 主要风险

1. **空间认知负担**：分支过多时，用户不知道当前正在编辑哪条线。
2. **上下文污染**：分支之间若默认共享全部历史，结果会失去独立性。
3. **合并歧义**：把一个分支的结论带回主线时，可能混淆事实和假设。
4. **性能成本**：长对话、多分支和模型流式输出会导致渲染及存储压力。
5. **视觉喧宾夺主**：如果先做炫目的 3D 棋盘，用户会看不懂产品价值。

#### 建议的产品边界

- MVP 只支持一个工作区内的单人对话。
- “维度”先实现为：时间顺序、横向分支、分支间引用三种关系。
- 默认最多展示 5 条活跃分支，更多分支进入折叠/列表模式。
- 合并不是自动拼接原文，而是生成带来源的“合并摘要”或引用节点。
- 3D 透视、多人协作、自动博弈式代理留到验证核心使用价值后。

## 2. 目标用户与使用场景

### 2.1 目标用户

- 研究人员：比较不同研究假设、证据链和检索路径。
- 产品/工程人员：为一个需求探索多套设计或实现方案。
- 学习者：针对同一知识点从不同解释路径学习。
- 写作者：并行推进大纲、人物动机、情节分支。

### 2.2 首要场景

**方案决策**：用户提出“如何实现 X”，AI 给出方案 A；用户回到提问节点创建分支，改用成本优先约束得到方案 B；最后比较两个分支并生成带取舍的决策摘要。

### 2.3 非目标

- 不是传统即时通讯软件。
- 不是强规则的棋类游戏。
- 不是无限画布白板的替代品。
- 不在 MVP 中承诺自动验证所有事实或自动决定最佳分支。

## 3. 核心体验与交互模型

### 3.1 前端页面方向：对话优先，地图辅助

页面默认应像一个熟悉的聊天产品，而不是游戏棋盘：

```text
┌─────────────────────────────────────────────────────────┐
│ 工作区 / 会话标题             搜索  地图  设置         │
├───────────────────────────────┬─────────────────────────┤
│                               │                         │
│        普通对话区域            │   可选的时间线地图       │
│   消息气泡、输入框、附件        │   主线 / 分支 / 多盘关系 │
│                               │   威胁与冲突标记         │
│                               │                         │
└───────────────────────────────┴─────────────────────────┘
```

推荐默认状态：地图收起，只显示右上角“打开地图”按钮和当前分支名称。打开后，地图以右侧抽屉或浮层出现，占据约 30% 到 40% 宽度；聊天区域保持可读，不被压缩成窄栏。用户也可以将地图固定为侧栏，形成对话区与地图区的双栏布局。

地图不是消息列表的替代品，而是结构导航器：

- 节点使用短标题、图标和状态，不直接承载完整消息正文。
- 点击节点会定位到聊天中的对应消息，并在必要时打开详情抽屉。
- 分支显示为路线，时间向右推进；跨盘引用显示为连接线。
- 超过可读规模后自动折叠为分支摘要、数量和风险标记。

移动端默认只显示普通对话；地图作为全屏抽屉打开，支持时间线列表和简化关系图两种视图。

### 3.2 用户必须始终知道的状态

- 当前工作区和会话。
- 当前所在时间线及其父节点。
- 当前选中的节点。
- 新消息会写入哪条时间线。
- 当前请求继承了哪些上下文。
- 当前分支是否有未合并的结果。

### 3.3 5D 元素的重新定义

这些元素保留，但不再强迫消息承担棋子形状：

- **多盘互动**：多个主题、方案或任务空间之间的引用和结果传递。界面上表现为地图中的多个“盘面/工作区”，聊天中以带来源的引用卡呈现。
- **将军/威胁**：不表示输赢，而表示约束、冲突、风险或未解决问题。例如“预算约束与性能目标冲突”“该结论依赖未验证假设”。地图显示警示标记，聊天中显示可展开的风险卡。
- **穿越**：从历史消息或决策点创建分支，聊天内容仍保持普通消息样式。
- **棋子**：只用于结构摘要，例如决策、假设、证据、问题、工具结果等“语义标记”，而不是每条消息的视觉容器。

### 3.4 关键交互

### 3.5 核心操作

| 操作 | 入口 | 结果 |
| --- | --- | --- |
| 创建分支 | 消息菜单“从此处分支”或地图节点菜单 | 复制节点之前的有效上下文，创建新时间线 |
| 切换时间线 | 画布分支标签/时间线列表 | 更新编辑目标，不修改历史 |
| 继续对话 | 当前时间线输入框 | 在该时间线追加消息和模型响应 |
| 比较分支 | 选择两条或多条时间线 | 展示差异、共同前置节点和结论摘要 |
| 引用节点 | 节点菜单“引用到当前线” | 在当前线上插入带来源的引用事件 |
| 合并结论 | 比较面板“生成合并摘要” | 生成新摘要节点，不覆盖原始内容 |
| 标记威胁 | 消息/地图节点菜单“标记风险” | 创建带来源和状态的约束或冲突标记 |
| 重命名/归档 | 时间线菜单 | 管理复杂工作区 |
| 撤销/重做 | 全局工具栏 | 撤销可逆的编辑和布局操作 |

### 3.6 上下文策略

分支创建时提供三种上下文模式：

- **继承全部**：适合继续同一问题。
- **继承至此节点**：默认模式，保留父节点之前的消息。
- **仅引用选中节点**：适合清理上下文或做独立实验。

上下文模式必须在发送前可见，并允许用户展开查看最终发送给模型的消息集合。

## 4. MVP 范围

### 4.1 必须实现

- 创建、重命名、归档会话和时间线。
- 在任意节点创建分支。
- 在当前时间线上发送消息并接收流式响应。
- 画布与列表双视图，支持缩放、平移和定位当前节点。
- 普通聊天作为默认主界面，地图可收起、展开和固定。
- 节点详情、来源标记、上下文预览。
- 两条时间线的并排比较。
- 多盘/工作区之间的引用卡和基础关系线。
- 威胁/风险标记及其解决状态。
- 以新摘要节点完成显式合并。
- 本地自动保存、错误恢复和导入/导出 JSON。

### 4.2 暂不实现

- 多人实时协作和权限系统。
- 自动跨分支合并原始消息。
- 3D 棋盘、复杂相机和空间音效。
- 多模型自动竞赛和自动选择赢家。
- 依赖外部知识库的强一致事实校验。

### 4.3 MVP 验收标准

1. 用户可以在 30 秒内从任一节点创建分支并明确看到当前编辑线。
2. 分支不会改变父时间线已有内容。
3. 刷新页面后，工作区、节点、分支关系和未完成状态可恢复。
4. 比较视图能指出两条分支的共同祖先、不同节点和各自结论。
5. 合并操作始终保留来源，不覆盖任何原始消息。
6. 1000 个节点、20 条时间线的本地数据加载后，首屏交互仍可用。

## 5. 技术架构建议

### 5.1 推荐技术栈

- 前端：React + TypeScript + Vite。
- 对话界面：React + TypeScript，消息流采用虚拟列表，保证长对话可滚动。
- 地图：优先使用 DOM/SVG 或 React Flow 类节点画布；MVP 不引入 WebGL。
- 状态：Zustand 或等价的事件化状态层。
- 数据校验：Zod。
- 本地持久化：桌面使用 Tauri + SQLite，Web 使用 IndexedDB；导出格式为版本化 JSON。
- 后端：Node.js + TypeScript，提供会话、模型代理、流式响应和同步接口。
- 测试：Vitest、Playwright。

### 5.2 框架选择理由

推荐 **React + TypeScript + Vite** 作为 MVP，而不是一开始使用游戏引擎：

- 普通对话、输入框、抽屉、菜单和无障碍交互都属于应用 UI，React 生态更成熟。
- 地图只需要局部图形交互，DOM/SVG 足够支持缩放、拖拽、选中和连线。
- 未来如果地图需要更复杂的空间效果，可以将地图模块独立替换为 Canvas/WebGL，不影响聊天域。
- React Native 或 Electron 不应在第一阶段提前引入；先验证 Web 端产品闭环。

不建议首版使用 Phaser 或 Three.js 作为整体框架。它们适合游戏渲染，但会增加普通文本、输入法、可访问性和窗口布局的实现成本。只有在地图本身成为高频沉浸式操作界面后，才值得评估 WebGL。

### 5.3 分层

```text
UI / Canvas
  -> Conversation UI / Map UI
  -> Interaction Commands
  -> Domain Store
  -> Event Log + Materialized View
  -> Persistence Adapter
  -> Model Gateway / Sync API
```

采用事件记录和派生视图的原因是：分支、撤销、回放和审计都需要知道“发生过什么”，而不是只保存最后一个列表状态。

### 5.4 核心数据模型

```ts
type TimelineId = string;
type NodeId = string;

type Timeline = {
  id: TimelineId;
  sessionId: string;
  name: string;
  parentTimelineId?: TimelineId;
  forkedFromNodeId?: NodeId;
  contextMode: "all" | "until-node" | "selected-only";
  status: "active" | "archived";
  createdAt: string;
  updatedAt: string;
};

type ConversationNode = {
  id: NodeId;
  timelineId: TimelineId;
  parentNodeId?: NodeId;
  relation?: "main" | "branch" | "focused-inquiry";
  inquiryRootId?: NodeId;
  focusSelection?: {
    sourceNodeId: NodeId;
    text: string;
    start?: number;
    end?: number;
    contentHash: string;
  };
  kind: "user" | "assistant" | "system" | "tool" | "reference" | "merge";
  content: string;
  sourceNodeIds?: NodeId[];
  model?: string;
  status: "pending" | "streaming" | "complete" | "failed";
  createdAt: string;
  metadata: Record<string, unknown>;
};

type DomainEvent =
  | { type: "timeline.created"; timeline: Timeline }
  | { type: "timeline.forked"; timeline: Timeline }
  | { type: "node.created"; node: ConversationNode }
  | { type: "node.updated"; nodeId: NodeId; patch: Partial<ConversationNode> }
  | { type: "merge.created"; node: ConversationNode; sourceTimelineIds: TimelineId[] };
```

### 5.5 前端模块边界

```text
src/
  app/                 路由、主题、全局错误边界
  features/chat/       消息列表、输入框、流式响应、引用卡
  features/map/        地图抽屉、时间线、分支和跨盘连线
  features/inspector/  节点详情、上下文预览、威胁处理
  domain/              Timeline、Node、Threat、Merge 等领域模型
  state/               命令、事件、派生视图和选择状态
  infrastructure/      SQLite/IndexedDB、模型网关、导入导出
```

聊天和地图通过领域事件通信，不直接互相读取组件内部状态。例如地图选中节点只发布 `node.selected`，聊天区负责响应并滚动到对应消息；创建分支由领域命令完成，两种 UI 都可以触发。

### 5.6 分支语义

分支不复制历史节点实体，只记录 `forkedFromNodeId` 和上下文规则。渲染和模型请求时通过祖先链计算有效上下文，避免复制导致存储膨胀。若未来需要高性能读取，再增加物化快照。

### 5.7 模型网关

模型调用统一经过 `ModelGateway`：

- 输入：可追踪的上下文节点集合、模型配置、生成参数。
- 输出：流式 token 事件、完成事件、错误事件、用量信息。
- 约束：前端不直接持有供应商密钥；每次请求保存可重放的请求元数据。

## 6. 关键实现细节

### 6.1 画布性能

- 节点详情和画布节点分离，画布只渲染摘要。
- 节点超过阈值时启用虚拟化或分段渲染。
- 流式响应只更新当前节点，不触发整个图重算。
- 布局结果缓存，只有拓扑变化时重新计算。

### 6.2 一致性与恢复

- 每个命令生成唯一 `eventId`，写入成功后再更新派生状态。
- 流式响应中断时保留已收到内容，并标记为 `failed` 或 `interrupted`。
- 自动保存采用节流写入；关闭前执行一次同步 flush。
- 导入 JSON 时先校验版本和引用完整性，再写入数据库。

### 6.3 安全与隐私

- API 密钥只存在服务端或用户本地安全存储，不进入导出文件。
- 导出默认脱敏运行时元数据，可由用户显式选择包含。
- 节点引用和合并摘要必须可追溯，避免“无来源结论”。
- 对外分享前提供“复制为新工作区”，避免无意暴露整个历史。

## 7. 迭代路线

### Phase 0：概念验证

- 静态画布、节点和分支交互原型。
- 用假模型响应验证“回到节点再分支”的理解成本。
- 目标：5 名用户完成方案比较任务，确认用户能理解当前时间线。

### Phase 1：MVP

- 接入单一模型供应商。
- 完成本地持久化、流式响应、分支、比较、合并摘要。
- 加入基础错误恢复、导入/导出和端到端测试。

### Phase 2：可用性增强

- 多模型并列响应。
- 节点标签、搜索、过滤和引用导航。
- 时间线折叠、分支排序和工作区模板。

### Phase 3：协作与智能化

- 多人协作、权限和评论。
- 自动发现冲突、总结差异和建议合并点。
- 可选的 3D/空间化视图，仅作为第二种视图，不替代列表视图。

## 8. 验证指标

### 产品指标

- 用户首次成功创建分支的时间。
- 一次任务中被保留的有效分支数量。
- 比较视图使用率和合并摘要采纳率。
- 因“找不到当前上下文”产生的退出率。

### 工程指标

- 画布交互 P95 延迟小于 100ms（普通规模工作区）。
- 首屏可交互时间小于 2.5 秒（不含模型响应）。
- 自动保存成功率不低于 99.9%。
- 分支和合并相关端到端测试覆盖关键路径。

## 9. 待决策问题

以下问题在开始 Phase 1 前需要明确：

- 首个模型供应商和流式协议。
- 是否只做本地优先，还是 MVP 就支持账号同步。
- 比较视图是按节点差异、语义差异，还是两者并列。
- 合并摘要由固定模板生成，还是允许模型生成并要求人工确认。
- 是否把工具调用、检索结果和附件纳入第一版节点类型。

## 10. 建议的下一步

1. 先实现一个不接模型的交互原型：预置节点、创建分支、切换分支、比较和合并。
2. 用真实任务做可用性测试，验证用户是否理解“当前写入哪条线”。
3. 再接入模型网关和本地持久化，避免在交互模型未验证前投入后端复杂度。
4. 通过验收标准后，再决定是否值得投入 3D 棋盘和多人协作。
